## 一、核心架构选择

### 1.1 两种架构对比

| 维度 | Sub-Agent（子智能体） | Agent Teams（智能体团队） |
|------|---------------------|------------------------|
| 任务分配 | 主Agent分配任务 | 共享任务列表 |
| 通信方式 | 仅返回最终结果 | 成员可直接对话 |
| 上下文 | 隔离（适合隐私） | 共享（适合协作） |
| 持续性 | 临时创建销毁 | 团队长期存在 |
| 状态管理 | 无共享状态 | 共享状态 |
| 适用场景 | 独立任务 | 持续协商 |

### 1.2 AIX一人公司Agent的架构选择

**核心问题**：10大能力模块如何编排？

| 能力模块 | 架构选择 | 理由 |
|---------|---------|------|
| 客服响应 | Sub-Agent | 独立对话，上下文隔离 |
| 内容生成 | Agent Teams | 需要持续协商（选题→创作→优化） |
| 项目管理 | Agent Teams | 共享任务列表，并行推进 |
| 财务记账 | Sub-Agent | 独立任务，隐私敏感 |
| 数据分析 | Sub-Agent | 独立分析，输出报告 |
| 日程管理 | Sub-Agent | 独立调度，输出时间表 |
| 客户管理 | Agent Teams | 多Agent协作（分析→推荐→触达） |
| 营销推广 | Agent Teams | 多步骤协作（策划→制作→发布） |
| 文档处理 | Sub-Agent | 独立任务，输出文档 |
| 知识管理 | Agent Teams | 多Agent协作（采集→整理→检索） |

**混合架构**：
```
一人公司Agent编排器
├── Sub-Agent集群（独立任务）
│   ├── 客服Agent
│   ├── 财务Agent
│   ├── 数据Agent
│   ├── 日程Agent
│   └── 文档Agent
└── Agent Teams（协作任务）
    ├── 内容Team（选题+创作+优化）
    ├── 项目Team（规划+执行+跟踪）
    ├── 客户Team（分析+推荐+触达）
    ├── 营销Team（策划+制作+发布）
    └── 知识Team（采集+整理+检索）
```

## 二、5种编排模式应用

### 2.1 模式1：链式调用

**定义**：顺序执行，上步输出即下步输入

**AIX应用**：
```
客服响应链式流程：
用户问题 → 意图识别 → 知识检索 → 方案生成 → 回复生成 → 发送通知

Coin Hour链：
数据采集 → 计算产出 → 价格更新 → 交易结算 → UTXO记账
```

**那耶村应用**：
```
游客导览链：
游客入场 → 需求分析 → 路线规划 → 文化讲解 → 服务推荐 → 反馈收集
```

### 2.2 模式2：意图路由

**定义**：按任务属性智能分发

**AIX应用**：
```
用户输入 → 意图识别 → 路由分发
                    ├── 客服意图 → 客服Agent
                    ├── 内容意图 → 内容Team
                    ├── 财务意图 → 财务Agent
                    ├── 分析意图 → 数据Agent
                    └── 其他意图 → 通用Agent
```

**关键设计**：意图分类器作为路由中心

**那耶村应用**：
```
游客输入 → 意图识别
          ├── 问路 → 导览Agent
          ├── 订房 → 民宿Agent
          ├── 找吃 → 美食Agent
          ├── 购物 → 特产Agent
          └── 投诉 → 客服Agent
```

### 2.3 模式3：并行化

**定义**：独立子任务同步推进

**AIX应用**：
```
内容生产并行化：
┌── 选题分析 ──┐
├── 素材搜集 ──┼──→ 内容合成
├── 竞品调研 ──┤
└── 受众分析 ──┘

数据分析并行化：
┌── 销售数据 ──┐
├── 用户数据 ──┼──→ 报告生成
├── 市场数据 ──┤
└── 财务数据 ──┘
```

**Coin Hour计算并行化**：
```
每个AIX Box并行产出：
┌── Box 1: 1 CH/hour ──┐
├── Box 2: 1 CH/hour ──┼──→ 总产出汇总
├── Box 3: 1 CH/hour ──┤
└── Box N: 1 CH/hour ──┘
```

### 2.4 模式4：编排者-执行者

**定义**：主智能体统筹分工（主流生产架构）

**AIX应用**：
```
一人公司编排器（主Agent）
    ├── 任务分解
    ├── 分发执行
    ├── 进度监控
    └── 结果整合
        ↓
    执行Agent集群
    ├── 客服执行Agent
    ├── 内容执行Agent
    ├── 财务执行Agent
    └── ...

工作流：
用户需求 → 编排器分解 → 分发执行 → 监控进度 → 整合结果 → 反馈用户
```

**与OPC Orchestrator对齐**：
```
OPC Orchestrator → 一人公司编排器
    ├── 判断用户阶段
    ├── 判断熟悉程度
    ├── 选择交互模式
    └── 决定下一步调用哪个Skill

一人公司编排器 → 执行Agent
    ├── 判断任务类型
    ├── 分解为子任务
    ├── 分发给执行Agent
    └── 整合执行结果
```

### 2.5 模式5：生成-评估循环

**定义**：多轮迭代优化输出

**AIX应用**：
```
内容质量循环：
生成初稿 → 质量评估 → 优化建议 → 修改重写 → 再次评估 → ... → 最终稿

客服质量循环：
生成回复 → 满意度预测 → 调整语气 → 再次生成 → ... → 发送回复

MVP验证循环：
设计MVP → 用户测试 → 反馈分析 → 迭代优化 → 再次测试 → ... → 确认方案
```

**Self-Improving机制**：
```
任务执行 → 结果评估 → 失败分析 → 改进原子任务 → 再次执行
    ↑                                                    ↓
    └────────── 自动进入下一轮 ←───────────────────────┘
```

## 三、设计原则：按"上下文"而非"角色"拆分

### 3.1 错误示例（按角色拆分）

```
❌ 错误：按角色拆分
├── 设计师Agent
├── 编辑Agent
├── 排版Agent
└── 发布Agent

问题：
- 信息在传递中衰减
- 上下文丢失
- Agent数量爆炸
```

### 3.2 正确示例（按上下文拆分）

```
✅ 正确：按上下文拆分
├── 内容创作上下文
│   ├── 选题阶段
│   ├── 创作阶段
│   └── 优化阶段
├── 客服对话上下文
│   ├── 问题识别阶段
│   ├── 方案生成阶段
│   └── 回复执行阶段
└── 财务处理上下文
    ├── 数据采集阶段
    ├── 记账处理阶段
    └── 报表生成阶段
```

### 3.3 AIX一人公司Agent的正确拆分

| 上下文 | 阶段 | 任务 |
|--------|------|------|
| **游客服务上下文** | 识别阶段 | 意图识别、需求分析 |
| | 执行阶段 | 导览、推荐、预订 |
| | 反馈阶段 | 满意度收集、问题记录 |
| **内容生产上下文** | 策划阶段 | 选题、调研、受众分析 |
| | 创作阶段 | 大纲、正文、配图 |
| | 优化阶段 | SEO、敏感词、可读性 |
| | 发布阶段 | 平台适配、定时发布、效果追踪 |
| **Coin Hour结算上下文** | 产出阶段 | 持有计算、产出记录 |
| | 交易阶段 | 价格计算、交易匹配、结算执行 |
| | 记账阶段 | UTXO记录、审计日志 |

## 四、与之前讨论的技术整合

### 4.1 与Skill Graphs 2.0整合

```
Skill Graphs 2.0（技能分层）
    ↓ 定义原子/分子/复合任务
Multi-Agent编排（任务执行）
    ↓ 将复合任务拆解为Agent协作
具体执行（原子任务）
    ↓ 由单个Agent执行

```

**映射关系**：
| Skill Graphs层级 | Multi-Agent编排 |
|------------------|-----------------|
| 原子任务 | 单Agent执行 |
| 分子任务 | 链式调用/并行化 |
| 复合任务 | 编排者-执行者/Agent Teams |

### 4.2 与OPC方法论整合

```
OPC方法论（业务流程）
    ↓ 定义做什么
Multi-Agent编排（技术实现）
    ↓ 定义怎么做
具体Agent执行（实际工作）
    ↓ 输出结果
Coin Hour结算
```

**OPC阶段 → 编排模式映射**：
| OPC阶段 | 编排模式 |
|---------|---------|
| 01资源盘点 | 并行化（多类别并行） |
| 02利基定位 | 生成-评估循环（多方案比较） |
| 03价值主张 | 链式调用（Jobs→Pains→Gains） |
| 04商业模式 | 编排者-执行者（Lean Canvas填充） |
| 06 MVP设计 | 生成-评估循环（迭代优化） |
| 07转化闭环 | 链式调用（触达→承接→成交） |

### 4.3 与Awareness-Local整合

```
Multi-Agent编排器
    ↓ 任务分配
执行Agent
    ↓ 需要记忆
Awareness-Local（共享记忆）
    ├── 客服记忆（隔离）
    ├── 内容记忆（共享）
    └── 财务记忆（隔离）
```

**记忆隔离策略**：
| Agent类型 | 记忆策略 |
|----------|---------|
| Sub-Agent | 独立记忆（隔离） |
| Agent Teams | 共享记忆（共享任务列表） |

## 五、一人公司Agent编排器设计

### 5.1 总体架构

```
一人公司编排器（主Agent）
│
├── 意图路由中心
│   ├── 用户输入 → 意图识别 → 路由分发
│   └── Coin Hour消费路由
│
├── Sub-Agent执行池
│   ├── 客服Agent（链式调用）
│   ├── 财务Agent（链式调用）
│   ├── 数据Agent（并行化）
│   ├── 日程Agent（链式调用）
│   └── 文档Agent（链式调用）
│
├── Agent Teams协作池
│   ├── 内容Team（生成-评估循环）
│   ├── 项目Team（编排者-执行者）
│   ├── 客户Team（编排者-执行者）
│   ├── 营销Team（编排者-执行者）
│   └── 知识Team（并行化）
│
└── 共享状态管理
    ├── 任务列表（Agent Teams共享）
    ├── 进度追踪
    └── Coin Hour计费
```

### 5.2 工作流程

```
用户需求 → 意图路由 → 任务分解 → Agent分发 → 执行监控 → 结果整合 → Coin Hour结算
    ↓           ↓          ↓           ↓           ↓           ↓            ↓
   输入      识别意图   编排器分解   分发执行   实时监控   整合输出      计费记录
```

### 5.3 Coin Hour编排计费

| 编排模式 | Coin Hour消耗 |
|---------|--------------|
| 链式调用 | 每步1-5 CH，总和计算 |
| 意图路由 | 路由1 CH + 执行费用 |
| 并行化 | 最长路径计费 |
| 编排者-执行者 | 编排10 CH + 执行费用 |
| 生成-评估循环 | 每次5-10 CH，循环计费 |

## 七、关键设计原则总结

### 7.1 能不拆就不拆

```
❌ 过度拆分：
用户问路 → 意图Agent → 位置Agent → 路线Agent → 导览Agent → 输出
问题：信息衰减、上下文丢失

✅ 最小拆分：
用户问路 → 导览Agent（完整上下文）→ 输出
优势：信息完整、响应快速
```

### 7.2 按上下文拆，不按角色拆

```
❌ 按角色拆：
设计师Agent → 编辑Agent → 排版Agent
问题：每个Agent只懂一部分

✅ 按上下文拆：
内容创作上下文（完整流程）→ 发布执行上下文（完整流程）
优势：每个上下文内信息连续
```

### 7.3 上下文隔离 vs 共享

| 场景 | 策略 |
|------|------|
| 客服对话（隐私） | 隔离（Sub-Agent） |
| 内容协作（共享） | 共享（Agent Teams） |
| 财务记账（敏感） | 隔离（Sub-Agent） |
| 项目管理（协作） | 共享（Agent Teams） |

## 八、与哈耶克视角的关联

### 8.1 编排器 = 中央计划？NO

**关键设计**：
- 编排器不替用户决策，只协助执行
- 编排器不集中知识，只协调分散Agent
- 编排器不控制结果，只优化流程

**符合哈耶克**：
```
传统编排器（中央计划）：
编排器 → 决定一切 → 执行Agent → 输出

AIX编排器（自发秩序）：
用户需求 → 编排器分解 → Agent竞争执行 → 最优结果
         ↑                ↑
       用户决策        分散知识协调
```

### 8.2 Agent Teams = 自发秩序？

**符合条件**：
- 成员可自由对话（不是中央控制）
- 任务列表共享（信息传递）
- 并行工作（分散知识利用）

**Agent Teams是哈耶克式协作的技术实现**。
