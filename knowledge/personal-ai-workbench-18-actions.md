## 🎯 一句话核心

> "Claude用得好不好，已经不太取决于你会不会写提示词了。更多时候，要看你有没有给它一个稳定的工作现场。"

---

## 🏗️ 六层架构

```
第一层：工作区（Project拆分）
第二层：身份与规则（个人说明 + Custom Instructions）
第三层：任务入口（目标卡 + 先问问题）
第四层：输出标准（样例 + 长度 + 格式）
第五层：上下文治理（隔离 + 清理 + 过期）
第六层：反馈回路（反方评审 + 压力测试 + 复盘）
```

## 📋 18个动作速查表

| 层 | 动作 | 解决的问题 |
|----|------|-----------|
| 工作区 | 1. 建3个Project，不要混用一个chat | 给不同任务划边界 |
| 身份 | 2. 写一份个人说明（300-500字） | 让Claude知道角色、目标、背景 |
| 行为规则 | 3. 把个人说明转成Custom Instructions | 固化默认协作方式 |
| 任务定义 | 4. 不只问定义，而是给出真实任务场景 | 让Claude参与解题，不是背百科 |
| 需求澄清 | 5. 复杂任务开始前先让它问问题（最多3个） | 少靠平均经验猜 |
| 输出样例 | 6. 给3-5段风格样本 | 把"像我"变成可学习样例 |
| 反方反馈 | 7. 让它反向评审方案，再做支持方论证 | 挖出隐含假设 |
| 推理预算 | 8. 复杂问题打开Extended Thinking | 给困难任务更多推理空间 |
| 任务说明生成 | 9. 让Claude先替Claude写任务说明 | 把模糊需求改成可执行任务单 |
| 输出预算 | 10. 指定输出长度（如"不超过150字"） | 控制阅读成本和调用成本 |
| 输出噪音 | 11. 去掉客套开场、重复总结、无效免责声明 | 让结果更干净 |
| 长期上下文 | 12. 不要每次重新解释自己 | 把稳定信息放进工作区 |
| 上下文隔离 | 13. 新话题开新chat | 避免旧任务污染新任务 |
| 学习方法 | 14. 用类比和费曼法解释复杂概念 | 检查是否真的理解 |
| 真实计划 | 15. 用真实偏好和约束做计划 | 避免生成通用方案 |
| 数据复盘 | 16. 用真实数据做开支、时间或项目分析 | 让建议落到证据上 |
| 个人反思 | 17. 先提问、再复述、最后给观�� | 不急着给建议 |
| 决策压力测试 | 18. 投入前压力测试商业想法或关键方案 | 提前暴露失败点 |

## 🚀 最小版本（8步启动）

### 第一步：建3个Project
- **Work**：工作项目、技术方案、会议、客户沟通
- **Writing**：文章、公众号、标题、选题、风格样本
- **Learning**：论文、课程、概念理解、读书笔记

### 第二步：写个人说明（300-500字模板）
```markdown
# About me in this project

我的角色：
我主要做什么：
这个Project用来解决什么问题：

当前长期目标：
1.
2.
3.

我偏好的输出：
- 先结论，后依据和边界。
- 段落短，少套话。
- 不确定时直接标注不确定。

默认不要做：
- 不要重复我的问题。
- 不要编造来源。
- 不要为了显得全面硬凑三点。

遇到信息不足：
先问最多3个关键问题；如果可以合理假设，先写明假设再继续。
```

### 第三步：写流程卡片（3-5张）
每张卡写三件事：
1. 什么时候用
2. 按什么步骤做
3. 怎样算完成

示例：
```markdown
# 方案评审流程卡

适用场景：
当我要评审一个产品、架构、文章主线或商业想法时使用。

默认步骤：
1. 先复述方案的目标和约束。
2. 找出5个最可能失败的假设。
3. 给出反方视角，不要急着帮我圆。
4. 再给出最完整的支持理由，说明这个方案为什么可能成立。
5. 最后给出你的真实判断，并列出需要验证的证据。

完成标准：
输出需要区分事实、推测和建议；不能只给泛泛风险。
```

### 第四步：给3-5个高质量样本
别贪多，样本要能代表你想要的输出长什么样。

### 第五步：写目标卡
```markdown
# 目标卡

本次任务要完成什么：
不做什么：
完成证据是什么：
时间或篇幅预算：
什么时候应该停下来问我：
```

### 第六步：加默认入口规则
```
先不要开始。
请先问我最多3个关键问题，确认目标、边界和完成标准。
如果你认为可以直接开始，请先写出你的假设。
```

### 第七步：加完成标准
```
输出最后建议包含：
- 结论
- 依据
- 不确定点
- 需要我确认的地方
- 下一步建议
```

### 第八步：每周清理一次
- 哪些Instructions已经不准了
- 哪些知识库文件该删掉了
- 哪些流程卡被反复改，说明该重写了
- 哪些输出问题反复出现，应该补成新规则
- 哪些规则写了根本没用，说明太抽象或者放错了位置

## ⚠️ 边界警示

| 不能做 | 为什么 |
|--------|--------|
| 敏感信息进Project | 身份证、密钥、客户合同按组织规则处理 |
| 临时偏好变长期规则 | "这次写得短一点" ≠ "我永远喜欢短输出" |
| 知识库变旧Wiki | 旧资料不删、旧判断不打标、旧流程不维护 = 技术债 |
| 只让Claude顺着你 | AI很擅长把没想清楚的东西包装得像想清楚 |

## 💡 关键洞察

### 1. 从提示词到过程资产
> "提示词常常只解决一次输出，流程卡解决的是一类任务。"

### 2. 先问问题为什么有效
> "这是把需求澄清前置了。软件项目里，最贵的错误通常来自问题定义错了，而不是代码写慢。"

### 3. 上下文污染
> "长对话里更麻烦的情况是：模型还记着一堆已经不该影响当前任务的东西。"

### 4. AI作为回声壁
> "AI很擅长把一个还没想清楚的东西，包装得像已经想清楚。所以长期上下文里，一定要保留反方角色和证据要求。"
