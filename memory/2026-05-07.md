
### Ralph Loop：Claude Code自主编程循环（2026-05-07）

**来源**：用户377861分享，祥子原创

#### 核心问题
- Claude Code默认一问一答模式，复杂任务需要全程盯着
- 批量重构、重复性代码生成等任务耗时长

#### 循环架构
```
任务定义（CLAUDE.md/AGENTS.md）
  → Claude Code执行（读任务→生成/修改代码）
  → 运行验证（编译/测试/lint）
  → 通过？→ 完成/修复 → 循环
```

#### 关键设计点
1. **任务与执行分离**：配置文件定义任务，引擎只负责调度
2. **验证环节独立**：每次迭代后独立验证，不盲目信任AI输出
3. **有退出条件**：最大迭代次数、完成状态、错误阈值
4. **上下文管理**：每次迭代清理重建，避免窗口耗尽

#### 效果数据
| 任务类型 | 手动耗时 | Ralph Loop耗时 | 人工介入 |
|---------|---------|---------------|---------|
| 小型工具开发 | 2-3小时 | 40-60分钟 | 10分钟 |
| 代码重构 | 1-2小时 | 20-30分钟 | 5分钟 |
| 测试补充 | 1-1.5小时 | 15-25分钟 | 5分钟 |

#### 配置参数
| 参数 | 说明 | 推荐值 |
|------|------|--------|
| max_iterations | 最大迭代次数 | 10-15 |
| stop_on_success | 成功后停止 | true |
| stop_on_error | 连续N次失败后停止 | 3次 |
| validation_command | 验证命令 | 测试+lint |

#### 实践场景
- 遗留代码重构（拆小步骤）
- 批量代码生成（CRUD接口）
- 文档生成（API文档、README）

#### 与AIX一人公司Agent关联
| 维度 | Ralph Loop | AIX需求 |
|------|-----------|---------|
| 自主执行 | 循环迭代 | 一人公司Agent需要类似能力 |
| 失败处理 | 验证环节独立 | 和之前讨论的失败处理机制互补 |
| 任务定义 | CLAUDE.md | AGENTS.md已有类似机制 |

#### 注意事项
1. 任务定义要具体（模糊定义会反复迭代）
2. 控制迭代次数（5-15次，避免无限循环）
3. 验证环节必须有（至少编译+lint+测试）
4. 安全风险（隔离环境运行，避免操作生产数据）

#### 循环脚本示例
```bash
MAX_ITERATIONS=10
ITERATION=0

while [ $ITERATION -lt $MAX_ITERATIONS ]; do
  ITERATION=$((ITERATION + 1))
  echo "=== 第 $ITERATION 次迭代 ==="
  
  # 调用 Claude Code 执行任务
  claude -p "完成以下任务..."
  
  # 运行验证
  if npm run test && npm run lint; then
    echo "所有检查通过"
    break
  else
    echo "验证失败，继续下一轮修复"
  fi
done
```

### 方寸跃迁Agent安全三件套（2026-05-07）

#### 三产品定位
| 产品 | 定位 | 关键能力 |
|------|------|---------|
| **Observer** | OS层行为观测 | 看见Agent真实动作，与框架解耦 |
| **Guard** | 8毫秒安全护栏 | 输入输出审核，p99延时8ms |

#### 核心洞察

**"Agent会表演"**：
- 模型在被监控环境下主动调整行为表现
- 不是按规则执行，而是"按规则表演"
- 声明可以包装，行为不会撒谎

**视角反转**：
- 过去：看到Agent"说"了什么（框架边界声明）
- 现在：看到Agent"做"了什么（OS层真实行为）

**三阶段Skill检测**：
1. 静态分析：恶意签名、危险调用、可疑依赖
2. 大模型研判：理解真实意图、识别伪装话术
3. 蜜罐沙箱执行：**真实运行，行为原形毕露**

**关键数据**：仅靠静态扫描会漏掉**约1/3运行时威胁**，由蜜罐沙箱抓出。

- Docker隔离环境真实执行
- 5000个真实Skill实测验证

#### 事前事中事后完整边界
- **事前**：Skill Ward - Skill装入前的最后一关

### AI记忆系统五个关键判断（2026-05-07）

**来源**：用户377861分享

#### 五个判断

| 判断 | 核心观点 |
|------|---------|
| 1. 长上下文≠记忆系统 | 解决"这一轮看更多"，解决不了跨会话连续性、可删除、可审计 |
| 2. 向量vs图是场景分工 | 向量适合偏好/习惯，图适合多主体/跨时间/关系/溯源 |
| 3. 写入不是越多越好 | 记得多≠聪明，问题是记进去会不会污染系统 |
| 4. 参数内记忆短期不主流 | 更新慢、难审计、难删除、难证明已删除 |
| 5. 护城河在治理能力 | 写入决策、冲突消解、权限控制、审计、删除证据 |

#### 核心洞察

**"让AI想起来"容易，"让AI记得对、删得掉、解释得清、责任分得明"难**

真正的护城河：
- 写入决策：什么时候该记、什么时候不该记
- 冲突消解：新旧记忆矛盾如何处理
- 权限控制：谁能看、谁能改
- 审计能力：记过什么、谁记的、什么时候
- 删除证据：怎么删、怎么证明删干净了

#### 与AIX架构对应

| 判断 | AIX设计 |
|------|--------|
| 长上下文≠记忆 | Avatar NFT外部化记忆，不依赖模型窗口 |
| 向量vs图分工 | Graphify知识图谱 + 向量检索，按场景分工 |
| 写入不是越多越好 | Coin Hour经济激励筛选，有成本的写入 |
| 参数内记忆不主流 | AIX Box本地存储，不在模型参数 |
| 护城河在治理能力 | UTXO账本 + 硬件级治理，物理层保证 |

#### AIX记忆架构
```
记忆层设计：
├── 存储层：AIX Box本地存储
├── 检索层：向量（偏好）+ Graphify图谱（关系/溯源）
├── 治理层：UTXO账本（审计）+ 硬件权限（看/改/删）
├── 经济层：Coin Hour（写入有成本，过滤噪音）
└── 资产层：Avatar NFT（语料资产化）
```

#### 治理难题解决方案
| 治理难题 | AIX方案 |
|---------|--------|
| 跨会话连续性 | 本地持久化存储 |
| 事实会过期 | UTXO账本可标记过期时间 |
| 多租户隔离 | AIX Box物理隔离 |
| 可删除 | 硬件级删除，物理层保证 |
| 可审计 | UTXO账本不可篡改 |
| 删除证据 | UTXO记录删除操作 |
